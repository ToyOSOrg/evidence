######## What each verdict should be ########

Each row's job reads a global 2 MiB kernel leaf over frame A, points it at frame B and reads again with nothing
invalidated (the control), invalidates as the row asks, and reads a third time, one CPU, interrupts closed. The issuing
CPU answers its own shootdown by the same reach as every other CPU (tlb::shootdown -> SHOOTDOWN.serve(me, flush)).
The AMD bench has no PCID, so its kernel-half flush is flush_global (the PGE toggle) and its user-half one a CR3 reload.

HEAD, both benches: all three rows GREEN, judge exit 0.
   On the AMD bench the keeping row's GREEN is itself a reading that Zen 2 caches the leaf global: its user-half
   answer there is a CR3 reload, which drops every translation that is not global.
HEAD control_regs, both benches: GREEN, every CPU's cr4 carrying bit 7 (PGE) and bit 18 (OSXSAVE, which #871
   declares). Derived, not measured: round 1's readings plus bit 18, so cr4=0x00360ee8 on every T14 CPU (bit 17,
   PCIDE, set) and cr4=0x00340ee8 on every AMD CPU (bit 17 clear: Zen 2 enumerates no PCID). Another value the judge
   still passes is a finding for me, with the line.
HEAD, the T14, both boots' kernel logs: "control_regs: cpuN signature 0x806c1 microcode 0xbe" for every N, with
   nothing after 0xbe. 0xbe is Linux's reading of MSR 8BH on every T14 CPU (kernel/cpuvuln/fixtures/t14/msr.txt); any
   other revision, or a line naming the erratum, is a finding for me. No such line on the AMD bench: the read is Intel's.

M1, AMD (flush_tlb_all without PCID back to a CR3 reload): a_kernel_half_shootdown_drops_a_global_kernel_translation
   RED, judge exit 1, the job exiting 101 with "the shootdown's flush left the old frame's global translation";
   the other two GREEN. **This is the AMD-only reading that matters**: beside the head's GREEN on the same row it shows
   that the Zen 2 caches the leaf global, which a CR3 reload leaves, and that flush_global's PGE toggle, every AMD
   kernel-half shootdown's flush, drops it. No other boot on either bench can show both.
M3, AMD (Owed::Address's global arm removed): a_global_kernel_leafs_discharge_drops_it RED, "the write's discharge left
   the old frame's global translation"; the other two GREEN. Without PCID, m3 falls to the arm that invalidates only
   where the target root is loaded, and the syscall runs on its process's root: this red shows the global arm is the
   one that acts, not that the leaf is global (that is m1's).
M4, AMD (the user-half answer is flush_tlb_all again, the PGE toggle there): a_user_half_shootdown_keeps_a_global_kernel_translation
   RED, "the user-half shootdown dropped a global kernel translation"; the other two GREEN.

Any row RED with "the control: with nothing invalidated the second read did not see the first frame" is neither: that
   CPU held no translation to go stale, and that boot's mutation evidence is void. Report it as such.
A mutation that stays GREEN where RED is expected is a finding for me, with the boot's kernel log.
A shared-debug boot that panics, in `amdvi` or anywhere, is a finding for me, with its flash log.
